# Fix: 500MB agent-update upload returns "Internal server error"

## Root cause (confirmed)

1. **Cap is exactly 500 MiB** — `server/src/routes/agentUpdate.ts:21` sets `limits: { fileSize: 500 * 1024 * 1024 }`. A "500MB" package (500 MiB or 1 byte over) trips `MulterError('LIMIT_FILE_SIZE')`.
2. **Every error becomes a 500** — `server/src/index.ts:61-64` catch-all returns `{ error: 'Internal server error' }` for all errors with no `MulterError`/`err.status`/fs-error inspection. `dashboard/src/api/client.ts:22` throws `Error(data.error)`, so the dashboard shows exactly "Internal server error" (matches the report verbatim).

Related large-upload defects fixed in the same pass:
- `server/updates/` is never created (multer only auto-mkdirs for string destinations; here `destination` is a function → ENOENT → generic 500 on fresh machines).
- `deploy/nginx-monitour.conf` `/api/` block has **no `client_max_body_size`** (nginx default **1m** → 413 before Node in production) and 60s default proxy timeouts.
- Node `requestTimeout` default 300s kills 500MB uploads slower than ~1.7MB/s.
- `agent/src/main/updater.ts:59-64` downloads the package with `responseType: 'arraybuffer'` + `writeFileSync` (whole 500MB in agent RAM, 5-min timeout) — will OOM/fail when agents pull a large package.

Verified non-issues: `express.json({limit:'2mb'})` doesn't touch multipart; multer diskStorage streams to disk; multer 2.x deletes partial files on abort; dashboard `client.ts` sends FormData correctly and needs no changes.

## User decisions

- Include the agent download fix (streaming) — not deferred.
- New cap: **2 GiB default, configurable via env** (`MAX_UPLOAD_SIZE`, bytes, Zod in `config.ts`).

## Changes

### 1. `server/src/config.ts` — add env knob

Add to `envSchema` (after `LOG_LEVEL`):

```ts
/** Max agent-update upload size in bytes. */
MAX_UPLOAD_SIZE: z.coerce.number().int().positive().default(2 * 1024 * 1024 * 1024), // 2 GiB
```

`Config` type is inferred — no other change.

### 2. `server/src/routes/agentUpdate.ts` — use config cap, create updates dir

- Add `mkdirSync` to the `node:fs` import (line 2).
- Move the `upload` construction inside `agentUpdateRoutes(cfg)` so the limit comes from config, and ensure the dir exists once at router setup (multer's function `destination` never mkdirs):

```ts
export function agentUpdateRoutes(cfg: Config): Router {
  const router = Router();
  mkdirSync(getUpdatesDir(), { recursive: true });
  const upload = multer({
    storage: multer.diskStorage({
      destination: (_req, _file, cb) => cb(null, getUpdatesDir()),
      filename: (_req, file, cb) => cb(null, basename(file.originalname)),
    }),
    limits: { fileSize: cfg.MAX_UPLOAD_SIZE },
  });
```

- Delete the old module-level `upload` (lines 16–22). `upload.single('file')` on the POST route stays as-is (now closes over the local `upload`).

### 3. `server/src/index.ts` — map errors to real statuses + requestTimeout

- Add `import multer from 'multer';` (already a server dep; `err instanceof multer.MulterError` typechecks via `@types/multer`).
- Replace the catch-all handler (lines 60–64). Keep `"Internal server error"` **only** for genuinely unknown errors:

```ts
app.use((err: unknown, _req: express.Request, res: express.Response, _next: express.NextFunction) => {
  if (err instanceof multer.MulterError && err.code === 'LIMIT_FILE_SIZE') {
    const gb = cfg.MAX_UPLOAD_SIZE / 1024 ** 3;
    const label = Number.isInteger(gb) ? `${gb} GB` : `${gb.toFixed(1)} GB`;
    res.status(413).json({ error: `File too large — maximum upload size is ${label}` });
    return;
  }
  if (err instanceof multer.MulterError) {
    res.status(400).json({ error: `Upload failed: ${err.message}` });
    return;
  }
  const e = err as { code?: string; status?: number; statusCode?: number; message?: string };
  if (e?.code === 'ENOSPC') {
    res.status(507).json({ error: 'Server storage is full — cannot store the uploaded file' });
    return;
  }
  const status = e?.status ?? e?.statusCode;
  if (typeof status === 'number' && status >= 400 && status < 500) {
    res.status(status).json({ error: e.message || 'Bad request' });
    return;
  }
  log.error('Unhandled error:', err);
  res.status(500).json({ error: 'Internal server error' });
});
```

(`err.status`/`statusCode` also fixes `express.json`'s oversized-JSON 413 being reported as 500.)

- After `createServer(app)` (line 67):

```ts
httpServer.requestTimeout = 0; // Node's 300s default kills slow multi-hundred-MB uploads
```

### 4. `deploy/nginx-monitour.conf` — allow large bodies on `/api/`

Inside `location /api/` (after line 56 `proxy_set_header X-Forwarded-Proto $scheme;`):

```nginx
        client_max_body_size 2g;     # keep in sync with server MAX_UPLOAD_SIZE
        proxy_request_buffering off; # stream uploads; avoid double 500MB disk copy
        proxy_read_timeout 600s;
        proxy_send_timeout 600s;
```

### 5. `agent/src/main/updater.ts` — stream download to disk (no RAM buffer)

In `downloadUpdate()` (lines 54–67):

- Imports: replace `writeFileSync` with `createWriteStream` in the `node:fs` import (it's only used here); add `import { pipeline } from 'node:stream/promises';`.
- Replace the fetch + `writeFileSync` with:

```ts
const resp = await axios.get(manifest.downloadUrl.startsWith('http') ? manifest.downloadUrl : `${serverUrl}${manifest.downloadUrl}`, {
  responseType: 'stream',
  timeout: 0, // no cap — a 500MB+ package on a slow link legitimately takes a long time
});
try {
  await pipeline(resp.data, createWriteStream(filepath));
} catch (err) {
  await rm(filepath, { force: true }); // never leave a truncated installer behind (applyUpdate executes it)
  throw err;
}
```

(Add `rm` to the `node:fs` import.) `applyUpdate()` and callers unchanged.

### Not touched

- `shared/src/protocol.ts` — no message-type changes (REST errors keep the existing `{ error: string }` shape).
- Dashboard — `client.ts:22` already surfaces the server's `error` message; after the fix users see "File too large — maximum upload size is 2 GB" etc. No change needed.
